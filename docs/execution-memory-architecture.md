# 执行记忆架构：简化设计

状态：简化架构已实现于当前工作区，尚未部署到正在运行的 Pi；真实会话收益待验证。

## 核心决定

只新增“一份任务记忆”和“一个记忆管理模块”，复用现有工作流、身份绑定、上下文视图、session 持久化和压缩管理器。

不新增事件总线、独立数据库、完整事件溯源系统、周期快照系统、第二套调度器或独立无进展引擎。

保持单一扁平队列：architect 确定目标/边界，执行者自主一般技术选择并完成可验收交付，仅真实偏差重规划。任务按可交付结果切分，不按读取→修改→测试机械拆分；复用 task/constraints/files/acceptanceCriteria 表达目标、非目标、交付物与风险匹配的验收，不新增复杂 schema。必要事实调查先于冻结详细计划；architect 仍禁止直接工具取证，所需调查由普通 docs-commit 任务交接。不确定远期只留里程碑，在边界细化，不强制每项重规划。developer-test 不做发布/Git 收尾，docs-commit 通常最后统一一次。

## 一张结构图

```text
现有 WorkflowState ───────────────────────► 执行授权与任务验收
                                                   │
SDK 已保存的工具结果 ──► TaskMemoryRuntime ──► TaskMemory
                              ▲                    │
                 task_workflow(checkpoint/status)   ▼
                                     现有 role-recovery/context-budget
                                                   │
                                          模型上下文视图
```

原始 session 保存完整执行历史；TaskMemory 只是当前任务的结构化索引和工作记忆，不再复制一套完整历史。

## 1. TaskMemory：记住进展，不管理执行

新增纯模块 `src/task-memory.ts`，定义及校验以下数据：

- **身份**：session、workflow、task、产生记录时的 attempt/handoff 和恢复代次。
- **当前步骤**：正在做什么。
- **已记录成果**：做过什么、支持它的真实工具结果或产物引用。
- **验证**：实际观察到的结果、来源 entry ID、适用文件/版本及不确定性。
- **剩余工作**：尚未完成的验收项、阻塞和下一步。
- **来源水位与 revision**：revision 防止陈旧 checkpoint 覆盖；progressRevision 表示新增支持事实或声明文件版本变化，重复观察和改写措辞不算新进展。

严格区分：工具成功、测试通过、需求满足、任务验收。普通 stdout 出现 passed 不能自动成为已验证结论；模型无来源的描述只算声明。

TaskMemory 不保存任务 status，不修改角色、不派发、不重试、不授权 complete。验收继续走现有任务 acceptanceCriteria 和 complete/block，不重建正式证据、结构契约/clarify 或嵌套协议。

complete 可选 evidenceIds 引用实际成功工具来源，记录为 verificationEvidenceIds。这只证明真实历史工具观察，不证明需求全部满足或依赖版本当前有效，不能替代 completionSummary/implementationRationale/verification 中的验收文字。

## 2. TaskMemoryRuntime：唯一写入路径

新增 `extensions/task-memory-runtime.ts`，只负责记录、恢复和读取。

- 复用真实 run binding，在 `turn_end` 用 SDK 的 messageEntryId/toolResultEntryIds 记录已发生的观察；提议、tool_call 和 execution_start 不算成功。
- 自动记录成功和失败的有界结果摘要与来源，不只记录错误；保留最近16条普通观察与最多32项 checkpoint 关键引用，完整正文仍在原 session。旧来源退出近期索引后仍可按真实来源 ID 读取并登记到 checkpoint，不必重跑。
- 阶段完成、验证结束或产物生成后，模型可通过现有 `task_workflow` 的 `checkpoint` 更新当前步骤、成果和剩余项，不新增独立记忆工具，不要求频繁 checkpoint 或每次工具后登记。
- checkpoint 必须引用当前 branch 可核对的真实来源；通过现有绑定拒绝旧任务、旧回合或恢复身份的提交。revision 是写入并发版本，内容变更才递增；缺少 expectedMemoryRevision 时准确返回当前 revision 供补齐，不伪报陈旧写入。progressRevision 仅在新增支持事实或声明文件版本变化时递增，改写措辞不算进展。
- 读取复用 `task_workflow(status)`；可按记忆中的来源 ID 返回有界原结果。不能因为上下文裁掉了结果，就要求模型重新执行命令。
- 使用 `pi.appendEntry("pi-init-task-memory", snapshot)` 持久化，恢复时取当前 branch 上最后一份身份可信的完整快照。只缓存可重建状态，不另建日志或数据库。
- 工具观察按来源 entry ID 去重；当前 checkpoint 的来源是已绑定的请求/branch 锚点，不能引用尚未产生的自身工具结果。
- reload/compact 后只从宿主已持久化结果补录，不执行补偿式重跑。来源不存在则明确未知，不补造成功。
- 写入失败不改原工具结果，也不返回成功 ack；标记记忆不可用，在既有安全边界停止依赖这份记忆的自动推进。

原快照继续留在 session 中供审计，但不建立额外事件类型、reducer 重放链或每 N 次事件的独立快照机制。首版恢复允许扫描当前 branch，后续按来源水位增量处理。

## 3. 上下文：先放工作记忆，再放聊天片段

不新建复杂编译器类。在现有 `role-recovery.context` 最终投影处统一组合：

1. 用户目标、不可改变的约束和当前任务验收项。
2. 当前真实身份、恢复状态和未知副作用提示。
3. 最新 TaskMemory：已做、验证、未做、下一步及来源引用。
4. 最新完整工具组，以及预算允许的旧工具组。

`role-context-budget` 只负责完整工具组的预算装箱，不决定已知进展是否存在。最终检查上述必备信息及工具配对；不能只在日志里声称保留。

**预算不足时只允许两种结果：**

- 裁掉旧大正文，保留准确的工作记忆、成功/失败语义和可读取来源；不静默丢掉仍被引用的关键事实。
- 必备信息仍放不下，则沿现有 token 预算检查与压缩管理器处理；不能安全处理就明确暂停，不能发送缺失进展的输入继续空转。

不截断用户新指令，不修改宿主 system 消息。没有账本的旧会话标为 legacy/incomplete，继续现有安全保全策略，不把聊天总结冒充验证。

## 活动任务只有一条容量管理路径

真实会话重放发现：192 KB字节装箱在SDK仅约9%窗口占用时，就将151条任务视图压成18条；JSON体积还计入opaque thinkingSignature。这是丢失过程证据并重复调查的直接诱因，不是模型窗口耗尽。

当前真实executing任务通过原身份/branch校验后，不再应用字节滑动裁剪；角色交接隔离仍保留，实际token压力交给已有SDK预算监视器/压缩管理器。无需模型先提交checkpoint才能保留本任务历史。暂停、恢复、身份未确认等其他视图继续原有保守预算策略，记忆损坏仍停止自动推进。

近期记忆中的read/grep/find/ls按工具名、输入hash、输出hash和结果去重，保留最新来源，避免相同只读内容挤走不同成果。命令、codemode、写入等可能有副作用的调用不合并，不缓存/跳过实际执行，也不把去重计为进展。

## 证据失效怎么处理

- “历史通过”与“当前仍有效”分开存。来源变化只使适用性失效，不删除曾经通过的事实。
- HEAD 相同不代表工作区相同；关键证据按相关文件内容核对，新增/未跟踪文件也不能遗漏。stat 只作变化线索。
- 无法确定任意 shell 的依赖范围就标记 unverified，不假装能证明全仓库未变；需要复用时定向核对，不默认重跑。
- 查一次 Git 不会自动让所有测试失效；重复查状态、查同一历史或重写 checkpoint 不增加进展 revision。
- 不为 complete 或文档变化重复全仓验证；相关来源/配置未变可引用真实已有结果并说明适用范围，变化才针对性补测。低风险文案/展示可核对差异与产物；中风险局部行为验证相关测试及直接影响；高风险权限、数据或恢复路径不能省略失败与恢复边界。
- source entry 可读不代表属于当前 branch，更不代表获得当前 attempt 的执行授权。恢复门和未知结果保护不变。

## 重复操作怎么收敛

重复观察保护只在现有进展观察器内保守收敛，不新建检测引擎或调度器：仅识别 native read/grep/find/ls 的相同工具、输入 hash 和输出 hash，且身份、branch、executing 任务和角色匹配、无恢复/用户停止门时启用。新事实、真实非只读工具活动或任务/角色/session/branch 变化重置；status/checkpoint 改写不算新事实，失败不能混成成功观察，不推断 bash/codemode 副作用。先有界提醒，持续相同且无新事实才走既有暂停边界，不缓存或跳过实际工具执行，不新增自动模型回合。

最终 assistant 错误不自动 nudge；提醒不生成任务授权锚点，不能用提醒获得任务写入或完成权限。

任务耗时和工具数只是软信号，不是强制终止条件。不设置“最多查几次 Git”或“最多交接几次”的硬上限，不根据一条重复就自动停止，更不自动完成任务。同范围无新事实的重复阈值不是工具总数或任务时长上限；新内容、真实复测或用户要求复核都可能是合理重复。

## 实施顺序

1. **记忆先落地**：增加 TaskMemory 与唯一管理模块，接入真实来源、session 保存及恢复；不改变验收和调度。
2. **接通读写协议**：现有 task_workflow 增加 checkpoint，status 提供记忆及来源读取；公共角色 Skill 说明何时登记、如何复用。
3. **替换投影策略**：在现有 recovery/budget 模块固定工作记忆主干，只有大正文参与裁剪；沿用原压缩/停止边界。

goals/goalId 继续只表达归属，任务走同一扁平队列与dispatcher；正式证据、结构契约和旧嵌套协议已退役，旧来源通过统一恢复诊断处理，不自动恢复。

## 验收底线

- 巨大旧失败不能挤掉已记录的成功验证；连续 100 次投影后仍能看见成果、剩余项并读取真实来源。
- reload/compact 后成果不消失；fork/tree 不串记忆；旧 attempt、伪造来源、陈旧写入不能获得授权。
- 工具成功但记忆未保存时只能补录原结果，不能重跑；写失败明确暴露。
- 源码变化后历史结果仍可查，但不冒充当前有效；相同来源的重复观察不伪装进展。
- 超限时保留语义或明确暂停，不破坏工具配对，不修改原历史、不新建自动回合。
- 任务记忆不受黑匣子开关控制；不主动采集凭据、headers、环境变量或额外大正文。有限摘要来自已有工具结果，仍可能含原结果的敏感信息，与原 session 使用同一私有边界，分享前须检查。
- 通过现有全部回归，再用新真实会话比较重复调查/验证率和任务完成率；不承诺模型永不重复。

完成标准：不是“多一个记忆工具”，而是“原始历史可以变长，模型视图可以变短，任务进展不会随之消失”。
